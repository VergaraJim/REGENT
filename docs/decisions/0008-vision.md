# 0008 — Vision: seeing the screen, and non-thinking replies

## Status

Accepted, 2026-11-10

## Context

Regent can look at the screen when the user asks about it (spec §2, §5.7, §5.8). Two
things have to happen locally, with no network:

- a vision model has to read a screenshot and answer a question about it;
- the text model has to stop printing its reasoning when it is a hybrid model, because
  that reasoning has no place in a small chat window, in speech, or in the database.

Everything stays on the machine: the screenshot is turned into pixels in memory, read
once and dropped.

## Decision

### Engine

`crates/regent-app/src/engine/llama_vision.rs` implements the core's `VisionEngine`
trait with llama.cpp's multimodal library (mtmd), through `llama-cpp-2`'s `mtmd`
feature. The `mtmd` feature is enabled by `regent-app`'s default `llama` feature, so the
vision engine is compiled into the normal build and links no extra library.

`LlamaVisionEngine` owns a model loaded from the vision GGUF and a projector (mmproj)
loaded from its own file. **Every question opens a fresh llama.cpp context** and drops it
afterwards, so a screenshot never enters the chat's KV cache and never lengthens the
conversation's prompt. The context window is 4096 tokens, the image is downscaled before
it gets there, and answers are capped at `VISION_MAX_TOKENS` (300) in
`crates/regent-core/src/vision/mod.rs`. Sampling is top-k 40, top-p 0.95, temperature
0.2.

The prompt is the model's own chat template when it has one, with ChatML as the
fallback; the multimodal media marker is placed before the question.

### Loading and unloading

`crates/regent-core/src/vision/service.rs` runs one worker thread that owns the engine.
The model is loaded on the **first** `look_at_screen` call, not when Regent starts, and
it is dropped when no look arrives within the keep-alive. The keep-alive is the
**Unload after** setting (**Settings → Models → Vision model → Options**), 120 seconds by
default. Pressing **Stop** configures vision off, which unloads the model at once.

State changes (`off`, `idle`, `loading`, `ready`, plus an optional plain-language error)
are pushed to the frontend, which shows "Loading vision model…" and errors under the
composer.

### Capture

`crates/regent-app/src/screen/mod.rs` uses the `xcap` crate, behind the default `screen`
feature of `regent-app`. It captures the **primary monitor** (or the first monitor when
none reports itself as primary), downscales it in memory with a triangle filter so its
longest edge is at most **Max image size** (1024 px by default), converts RGBA to RGB8
and hands the pixels to the vision engine.

Pixels are never written to disk by Regent: no temporary file, no log line. Only the
answer text leaves the vision service; the chat model sees a tool row with that text.

Two caveats:

- **Wayland.** xcap captures through the desktop's screenshot portal. The portal may take
  over the capture and may show its own permission prompt, which Regent cannot suppress.
- **Regent's own window** is on the primary monitor, so it can appear in the screenshot.
  The window is 380×560 and carries no secret beyond what the user is looking at.

### Permissions

The messages are plain and platform-specific, generated by `capture_failed_message`:

- macOS: "Regent needs Screen Recording permission. Turn it on in System Settings →
  Privacy & Security → Screen Recording, then restart Regent."
- Wayland: "Regent couldn't capture the screen. Allow screen sharing when your desktop
  asks, then try again."
- Anything else: "Regent couldn't capture the screen."

With no monitor at all the answer is "No screen was found to look at."

### Non-thinking mode

For chat templates that mention `<think>`, `without_thinking`
(`crates/regent-app/src/engine/llama_chat.rs`) pre-fills an empty think block right after
the assistant header — the same trick Qwen3 uses with `enable_thinking=false`. A template
that never mentions `<think>` is left byte-for-byte alone, so other models see exactly
what their template produced.

Anything that still comes back inside `<think>…</think>` is filtered out by
`ThinkFilter` / `strip_think` (`crates/regent-core/src/chat/think.rs`). The chat service
runs the filter **before** the tool-call parser, so reasoning never reaches the visible
reply, the tool calls, speech (which is fed from the same token stream) or the database.
Summaries are filtered too. The vision engine applies the same pre-fill and strips
reasoning from its answers.

Harmony-style reasoning channels (gpt-oss's `analysis` channel) are **not** covered: only
the `<think>` markers are recognised.

## Consequences

- Native builds are longer: `mtmd` is part of the `llama` feature, so the default build
  compiles more of llama.cpp than the text engine alone.
- Linux builds need extra `-dev` packages for screen capture — the X11/Wayland/portal
  set listed in `.github/workflows/ci.yml` and in the README.
- `look_at_screen` is offered to the text model only when **both** the vision model and
  its projector are set; with one of them missing the tool is not in the prompt at all,
  and a look that does reach the service answers "Vision isn't set up. Choose a vision
  model and its projector in Settings."
- A hybrid model that ignores the pre-filled block still cannot leak its reasoning into
  the reply, speech or store, because the streaming filter is unconditional.
- The vision smoke test stays opt-in: `crates/regent-app/tests/llama_vision_smoke.rs`
  is `#[ignore]`d and needs `REGENT_TEST_VISION_MODEL` and
  `REGENT_TEST_VISION_PROJECTOR`.
